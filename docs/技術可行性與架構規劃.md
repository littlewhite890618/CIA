# CIA 專案 — IG AI 戀愛對話教練：技術可行性與架構規劃

## Context

產品目標是在 Instagram 私訊上提供 AI 角色陪聊 + 對話後教練回饋，長期累積使用者輪廓並與想想交友會員庫配對。

本文件是**可行性評估與架構決策**，不是程式實作計畫（專案目前是空資料夾，尚無程式碼）。目的是在寫第一行程式前，把會反向改寫產品設計的平台限制釘死，並確立技術選型與分期。

**結論：技術可行。最大風險不在技術，在 Meta 帳號與審核。**

### 已確認的使用者決策
- MVP 範圍：**陪聊 + 教練回饋**（不含輪廓萃取、配對、角色克隆）
- MVP 角色數：**先做 1 個角色**（見 §1.3 容量含義）
- MVP 不使用 n8n（見 §3.1）
- 主鏈路技術：**Python FastAPI 自建**
- LLM：**MVP 先用免費模型驗證流程**（見 §3.2）
- Meta / IG 準備狀態：**完全還沒開始**（無開發者帳號、無商業驗證、無專業帳號）
- 平台只用 Instagram；定位為「對話練習夥伴／教練」，不涉曖昧；profile 標註 AI

## 一、平台限制（已查證，2026/9）

### 1.1 24 小時訊息視窗 — 主動發訊的實際邊界

| 情境 | 可行 |
|---|---|
| 對從未發訊過的使用者主動開啟對話（cold outreach） | ❌ 不行 |
| 使用者發訊後 24h 內主動發訊（**不限一則、不需對方再開口**） | ✅ 可行 |
| 24h 之後主動發訊 | ❌ 不行 |

政策原文：「Businesses have up to 24 hours to respond to a user. **Messages sent within the 24-hour window may contain promotional content.**」— 連推廣內容都允許，代表視窗內**非**「一問一答」限制。

計時器在使用者每次發訊、或點擊 Quick Reply / Ice Breaker / Persistent Menu 時**重置為完整 24 小時**：

```
10:00  使用者發訊               → 倒數開始，效期至隔日 10:00
10:01  系統回覆                  ✅
10:30  系統再主動發一則          ✅ 不需等對方回覆，則數不限
14:00  使用者再次發訊            → 倒數重置，效期至隔日 14:00
隔日 15:00 系統嘗試發訊           ❌ 已逾期，API 報錯
```

→ 本產品幾乎不會撞到此限制（使用者主動來聊天，當天有聊就有整天可送報告）。唯一失效情境：**使用者聊完後逾 24 小時未再開口**。

→ **「靜默 25 分鐘後主動送邀請訊息」合法**，屬已開啟對話中的後續訊息，非 cold push。本產品天然符合此限制：使用者本就是主動來聊天的，視窗永遠由他們開啟。

其他限制：
- `HUMAN_AGENT` tag 可延長至 7 天，但 **Meta 明文限真人客服使用、禁止自動化**，有偵測機制 → 不可用於 AI 教練報告
- 2026/4/27 起 `CONFIRMED_EVENT_UPDATE`、`ACCOUNT_UPDATE`、`POST_PURCHASE_UPDATE` 三個 tag 已回傳 error 100

**應對（核心設計）：**
點擊 postback 按鈕會觸發 `messaging_postbacks` webhook 並**重開 24 小時視窗**。因此教練報告採「邀請 → 使用者點按 → 生成」流程：

```
靜默 25 分鐘 → 送一則極短邀請訊息 + Quick Reply「看今日報告」（仍在 24h 內）
             → 使用者點擊 → postback → 視窗重開 → 從容生成完整報告
Persistent Menu 常駐「生成今日報告」作為隨時索取的備援路徑
```

附帶效益：省 LLM 成本（沒人看的報告不生成）、體驗更好（使用者主動索取）、合規更穩（主動訊息僅一則短邀請）。

### 1.2 互動元件能力與限制
| 元件 | 數量上限 | 觸發 | 平台限制 |
|---|---|---|---|
| Persistent Menu | 建議 ≤5 項 | postback webhook 或開 URL | **僅手機版顯示** |
| Ice Breakers | 最多 4 題 | postback webhook | **僅手機版顯示** |
| ~~Quick Replies~~ | ~~最多 13 個~~ | ~~一般訊息事件~~ | ⚠️ **實測不可用，見下方訂正** |
| **Button Template** | 1–3 個按鈕 | **postback webhook** | 實測可用（手機 App 確認） |

> ⚠️ **2026-09-23 真機實測訂正：Quick Replies 在本專案的 API 上完全不可用。**
>
> 原表格寫「手機 + 桌面皆可」，據此把教練報告的邀請按鈕設計成 Quick Reply。
> 實作後真機測試發現**手機 App 與桌面瀏覽器都看不到任何按鈕**：
> `POST /{ig-id}/messages` 帶 `message.quick_replies` 會回 **HTTP 200 並正常拿到
> `message_id`**，訊息也確實送達，但按鈕不存在——Graph API 對不支援的欄位
> 是默默忽略而非報錯，從症狀完全看不出問題在哪。
>
> 同一支帳號、同一個端點改送 **Button Template**
> （`message.attachment.type=template` / `template_type=button` /
> `buttons[].type=postback`）則按鈕正常顯示，點擊後觸發 `messaging_postbacks`
> webhook，payload 正確送達（log 驗證：`收到 postback | payload='DIAG_BT_CLEAN'`）。
>
> 原判斷可能是把 **Messenger 平台**的 Quick Reply（確實支援桌面）與
> **Instagram 平台**的搞混——兩者 API 形狀幾乎相同但支援的元件不同。
> Meta 官方雖有 Instagram Quick Replies 文件頁，但與實測行為不符。

→ 報告索取路徑目前採 **Button Template**。桌面版是否顯示 Button Template 尚未驗證
（2026-09-23 的桌面測試是在 Quick Reply 版本做的，已失效）；若桌面版同樣不顯示，
表示**所有互動元件都只在手機 App 可用**，桌面使用者需要另尋路徑（例如請他們直接
回覆特定文字），這點需要另外驗證後再定案。

其他：訊息文字上限 1000 bytes（UTF-8）；單則最多 10 個 attachment；圖片 8MB、音訊/影片/檔案 25MB。中文 1000 bytes 約 330 字 → **教練報告必須切成多則訊息發送**。

> **1000 bytes 的出處**（2026-09-09 查證）：
> <https://developers.facebook.com/docs/instagram-platform/instagram-api-with-instagram-login/messaging-api/>
> 原文：*"Message text must be UTF-8 and be a 1000 bytes or less."*
> **單位是 bytes 不是字元**——以字元數估算會嚴重超標。

### 1.3 速率限制
- 官方文件：文字訊息 **100 calls/sec 每專業帳號**；含音訊/影片 10 calls/sec；Conversations API 2 calls/sec；留言私訊回覆 750 calls/hr
- **未公開的反垃圾行為門檻**：多家第三方工具商回報自 2024/10 起約 **200 則自動 DM/小時/帳號**。無官方文件背書，**必須實測驗證**，但先當規劃前提

> **速率限制的出處**（2026-09-09 查證）：
> <https://developers.facebook.com/docs/graph-api/overview/rate-limiting/>
> 原文：*"Your app can make 100 calls per second per Instagram professional account
> for messages that contain text, links, reactions, and stickers"*；
> 一般呼叫量為 *"Calls within 24 hours = 4800 × Number of Impressions"*。
>
> ⚠️ Instagram 的速率限制**不在** Instagram Platform 自己的文件區
> （`/docs/instagram-platform/rate-limits` 會回 404），而是併在 Graph API 總表裡。
>
> **關鍵區分**：官方公布的是「技術上限」（每秒呼叫數），本系統的用量遠低於它，
> 不會成為瓶頸。真正會擋住的是上面那條未公開的反垃圾門檻——而且撞到它的症狀
> 不是 API 回錯誤碼，而是**帳號被限制或停權**（2026-09-09、09-10 各發生過一次
> 開發者帳號被封鎖，需驗證手機才解封）。因此速率配額的實作寧可保守。

### 1.3.1 24 小時訊息視窗（平台端行為已實測）

Meta 對逾期發訊的實際回應（2026-09-10 繞過我方檢查直接呼叫 API 實測）：

```
HTTP 403
{"error": {"message": "這則訊息並未在允許的期間內傳送。",
           "type": "IGApiException", "code": 10, "error_subcode": 2534022}}
```

`code 10` 本身涵蓋多種權限問題，**必須靠 `error_subcode 2534022` 才能認出是視窗逾期**。
已據此在 `app/channels/instagram.py` 建立 `InstagramWindowExpired` 錯誤分類，
讓平台端拒絕能與我方主動擋下分開記錄——兩者不一致（例如時鐘偏移）本身就是
值得觀測的訊號。

**容量推論（若 200/hr 成立）：** 一場 session 機器人端約 20–30 則 → 單一角色帳號每小時僅能撐 7–10 場完整對話。
→ **角色帳號同時是吞吐量單位**，不只是人設多樣性。晚間尖峰 4 小時服務 500 場對話需 15–20 個角色帳號。這要進容量模型。

**對 MVP 單角色的直接影響：** 每小時上限約 7–10 場對話 → **MVP 只能做品質驗證，無法做規模驗證**。測試時須將同時線上人數控制在 10 人以內，否則會排隊或被限流。「這門生意跑不跑得動」必須等多角色階段才能回答。

### 1.4 揭露義務
- Messenger Platform 政策：自動化對話必須**在對話開頭**揭露為自動服務（不只是 profile 簡介欄）
- 2026/8 起 IG 對擬真人類 AI 人設帳號要求 AI-generated profile 標籤；未揭露會被限縮 Reels/Explore 推薦
→ **角色帳號難以靠自然觸及長粉**。獲客靠主品牌帳號／廣告／想想交友既有會員導流；角色帳號定位為服務端點而非流量端點

### 1.5 IGSID 身分範圍
IGSID **以專業帳號為範圍**：同一真人與角色 A、角色 B 對話會產生兩個不同 ID，無法自動關聯。
User Profile API 可取得 `username`、name、大頭貼、粉絲數、追蹤關係 → **可用 username 做跨角色身分串接**，但屬跨帳號身分關聯，**必須寫入服務條款揭露**。
限制：需使用者先發訊／點 Ice Breaker／用 Persistent Menu 才取得同意；被封鎖則無法讀取。

## 二、風險登記

| 風險 | 等級 | 緩解 |
|---|---|---|
| Meta App 停權導致全部角色同時斷線 | **存亡級** | 對話與輪廓全存自有 DB；IG 抽象為 channel adapter；評估角色分散於 2–3 個 Business Portfolio（此作法是否違反 Meta 條款**尚未查證**） |
| App Review 未過 | 高 | use case 以「AI 對話練習教練」框架送審，避免「陪聊／戀愛顧問／dating」字眼 |
| 平台政策收緊 | 中高 | Meta 已於 2026/1/15 禁止第三方通用 AI 助理進駐 WhatsApp。IG 無等價禁令但方向明確 → 預留 LINE 為第二通道（目標客群在台灣，LINE 更穩） |
| 200/hr 門檻使容量不足 | 中 | 第一階段實測驗證；設計時把角色帳號數當可調參數 |
| 未成年使用者 | 中 | Meta 已對 18 歲以下限制 AI 角色功能，需年齡把關機制 |
| 情感風險事件（自傷、情緒崩潰） | 高 | 獨立即時分類器 + 升級真人路徑 + 事件記錄。非 nice-to-have |

## 三、架構

### 3.1 分層
| 層 | 職責 | 技術 |
|---|---|---|
| Ingress | Meta webhook 接收、`X-Hub-Signature-256` 驗章、依 `entry[].id` 路由至角色 | Python FastAPI |
| Session | 對話狀態、24h 視窗、靜默計時、速率配額 | Redis + Postgres |
| 對話生成 | 角色扮演回覆 | 可插拔（見 §3.2）；正式版建議 Claude Sonnet 5 + **prompt caching** |
| 即時分析 | 偵測地雷、句點、安全風險 | 可插拔小模型，**旁路非阻塞** |
| 教練回饋 | 對話後報告生成 | 可插拔；品質基準線需用高階模型建立（見 §3.2） |
| 儲存 | 對話、角色、事件 | Postgres 16（沿用既有 docker-compose 模式） |
| 後台 | 角色管理、報告檢視、安全事件 | React（既有） |

**n8n 定位：MVP 不使用。** MVP 全部流程皆為事件驅動（webhook → 處理 → 回覆），無真正的排程批次需求。唯一類排程的「靜默 25 分鐘判定」以 FastAPI 背景 loop 定期掃 Postgres 即可（`last_message_at < now() - 25min AND invite_sent = false`），數十行程式碼且重啟後狀態不遺失。引入 n8n 反而多一個元件、多一個故障點、多一層跨系統除錯。

n8n 待 MVP 之後再接入：每日營運報表、配對跑批、想想交友資料庫同步、營運人員通知。屆時架構上不衝突。

**記憶架構：** 短期滾動對話窗 + 定期壓縮摘要；長期用結構化 `user_profile` JSONB。**初期不上向量庫** — 配對比對需要結構化欄位，向量相似度做不到。

### 3.2 LLM 選型：可插拔介面 + MVP 免費模型

**架構原則（第一天就要做）：** 抽象出 `LLMProvider` 介面，三條路徑（對話生成／即時分析／教練回饋）各自獨立設定模型。換模型應是改設定而非改架構。一開始做成本近乎零，事後補很痛。

**MVP 免費／低成本選項（以繁中人設扮演為前提）：**

| 選項 | 適合度 | 注意事項 |
|---|---|---|
| Google AI Studio (Gemini Flash) 免費層 | 最務實 | 有 RPM/RPD 限制，多角色並行測試可能卡住 |
| 本機 Ollama + Qwen 3 | 中文語感最好 | 需 GPU，須先確認開發機顯卡 |
| Groq 免費層 | 速度快 | 中文人設扮演偏弱 |
| DeepSeek | 非免費但極便宜 | 中文強，實務上可能優於「免費但難用」 |

**兩條路徑對品質的敏感度不同：**
1. **角色對話** — 免費模型驗證流程無虞。但需特別檢查「AI 味重」「翻譯腔」，這在陪聊產品是致命缺陷
2. **教練回饋** — **這是核心價值主張**。若用免費模型測出「建議很空泛」，將無法分辨是**產品概念不成立**還是**模型不夠好**，可能誤砍一個其實可行的產品

**因此：** 對話生成放心用免費層；教練回饋**至少用高階模型跑 20–30 份報告建立品質基準線**（花費約數百元台幣），作為後續比較的對照組。

### 3.3 資料模型草案
```
personas            角色：ig_account_id, name, gender, personality_card(jsonb),
                          system_prompt, status, capacity_weight
                    ← MVP 僅 1 筆，但仍建表，避免日後遷移
users               ig_username(跨角色串接鍵), consent(jsonb)
                    ← 年齡驗證委由 IG 平台把關（帳號已設 18+ 限制），系統不另存
user_persona_links  user_id, persona_id, igsid  ← IGSID 為帳號範圍，需此中介表
                    ← MVP 單角色時 igsid 即唯一鍵，但保留此表結構
sessions            user_id, persona_id, started_at, ended_at,
                    window_expires_at, last_message_at, invite_sent,
                    state, message_count
messages            session_id, direction, ig_message_id, content, sent_at, meta(jsonb)
realtime_signals    session_id, message_id, signal_type, severity, detail(jsonb)
coach_reports       session_id, requested_at, generated_at, delivered_at, content(jsonb)
safety_events       user_id, session_id, category, severity, handled_by, handled_at
rate_budget         persona_id, window_start, sent_count  ← 對應 200/hr 門檻
```
`user_persona_links` 是關鍵：IGSID 以角色帳號為範圍，必須有中介表才能把同一個人的多角色互動歸戶。

### 3.4 教練報告規格

> **依賴方向：報告要輸出什麼，反向決定對話過程要記錄什麼訊號。**
> 若先做對話系統再定義報告，會發現該收集的資料沒收集（例如要評「有沒有接住對方拋出的話題」，但對話當下未標記哪些是「拋出的話題」，事後只剩純文字難以分析）。因此本節須先於 Phase 2 定案。

#### 3.4.1 身分設計：獨立顧問，同一帳號

角色（陪聊對象）與顧問（回饋者）是**兩個獨立身分，共用同一個 IG 帳號**。

| | 角色 | AI 戀愛顧問 |
|---|---|---|
| 職責 | 扮演一個真實的人，自然對話 | 複盤與教學 |
| 語氣 | 口語、有情緒、短句多則 | 簡潔、結構化、長段落 |
| 稱呼使用者 | 依人設 | 「你」 |
| prompt | 只需專心扮演，**不含任何教學指令** | 只需專心分析 |

**不採用「角色本人切換成教練語氣」**：剛才的陪聊對象突然評價你，等於當場承認她一直在評估你，會破壞「安全、不尷尬的練習環境」這個核心願景，並讓使用者下次對話產生被評分的壓力。

**技術成本為零** — 同帳號、同 API、同 webhook，差別僅在使用哪一組 prompt 與訊息模板。附帶效益：兩組 prompt 可各自優化，角色的自然度與顧問的分析精準度不互相拖累。

#### 3.4.2 視覺區隔：固定抬頭

IG 私訊無任何排版能力（不能粗體、變色、卡片、底色），所有訊息視覺上完全一致。可用的區隔工具只有 emoji、符號畫線、固定文字組合三種。

顧問訊息一律以**完全相同**的抬頭開頭（寫死的字串常數）：

```
━━━━━━━━━━━━━━━
📋 AI 戀愛顧問 · 今日對話分析
━━━━━━━━━━━━━━━
```

「固定」是關鍵：抬頭永不變動，使用者才能在讀完內容之前就辨識出身分切換。若每次抬頭措辭不同，就退化成需要閱讀理解的訊息，辨識訊號大幅減弱。

同一套結構（emoji + 品牌名 + 訊息類型）可延伸至其他系統訊息：
```
⚠️ AI 戀愛顧問 · 系統通知
🎯 AI 戀愛顧問 · 練習建議
```

#### 3.4.3 報告結構

```
1. 今日對話摘要      聊了什麼、整體氣氛
2. 做得好的地方      1 點，直接引用使用者當時說的話
3. 可以調整的地方    1 點，引用原句 +「你說完這句後，她的回覆變短了」
4. 改寫示範 ★        「如果改成這樣說會更好：______」
5. 下次可以試試      一個具體、當天就能用的小技巧
```

**第 4 點是核心價值。** 抽象建議（「你要多聊她有興趣的話題」）沒有教學效果；具體改寫（「你說『喔這樣喔』，改成『欸這個我也想試試，你怎麼開始的？』就會延續下去」）才是產品的差異化所在。

#### 3.4.4 已定案的產品決策

| 決策 | 選擇 | 理由 |
|---|---|---|
| 評分形式 | **不給總分，只給具體建議** | 目標客群本有社交焦慮；練習環境若變成評分場會直接流失。與「獨立顧問」同屬降低被評價感的一致邏輯 |
| 篇幅 | **1–2 則，約 500 字** | IG DM 為手機情境，過長無人讀完。聚焦 1 優點 + 1 改進點 + 1 改寫示範 |
| 身分 | **獨立顧問、同帳號、固定抬頭區隔** | 見 3.4.1 |

#### 3.4.5 評分維度（內部分析用，不對使用者顯示分數）

| 維度 | 觀察什麼 |
|---|---|
| 提問品質 | 開放式 vs 封閉式比例、有無審問式連問 |
| 接話與延展 | 對方拋出的話題有無被接住、有無造成句點 |
| 情緒感知 | 有無讀懂對方的情緒訊號 |
| 自我揭露平衡 | 一直講自己 vs 一直問對方、有無過度自誇 |
| 分寸與界線 | 有無踩到地雷：索取聯絡方式、性暗示、約見面、評論外貌、貶低、抱怨前任 |
| 節奏 | 訊息轟炸（即時訊號）、訊息長度與發送頻率（報告階段由 `messages` 統計） |

> 2026-09-21 修訂：原七項（含「開場能力」，並將「接話能力」「話題延展」分列）改為六項，
> 以與 §3.4.6 的訊號種類對齊。原七項中沒有任何維度能容納最嚴重的一群地雷（L1～L6），
> 故新增「分寸與界線」；「開場能力」無對應訊號，移除。

除「節奏」的長度與頻率外，這些維度**必須由即時分析層標記並寫入 `realtime_signals`**，否則報告生成時無資料可用。
標記時機為 session 結束時對整段對話分析一次（2026-09-22 由逐則分析改定，理由見 openspec design.md 決策 6）。

#### 3.4.6 即時訊號定義

**地雷（`signal_type = landmine`）**：過早涉及身體話題、貶低型玩笑、連續發問如審問、過度自誇、抱怨前任、單次連發多則訊息轟炸、過快索取聯絡方式

**句點（`signal_type = conversation_killer`）**：只回「嗯／喔／哈哈」、連發封閉式問題、完全未回應對方拋出的話題

**亮點（`signal_type = highlight`）**：開放式提問、成功接住對方話題、適當的自我揭露、讀懂並回應情緒

亮點訊號同樣要記錄 —— 報告的「做得好的地方」需要它，且正向回饋對留存的作用不亞於糾錯。

## 四、分期執行

### Phase 0 — Meta 前置作業（**立即開始，關鍵路徑**）
Meta 這條路徑最長（商業驗證需公司文件，可能數週），必須與開發**並行**啟動。
1. 建立 Meta 開發者帳號與 Business Portfolio
2. 送出商業驗證（需公司登記文件）
3. 建立 App，設定 app icon、隱私政策 URL、app category
4. 建立 **1 個** IG 專業帳號（Business/Creator）作為 MVP 角色
5. 準備 App Review 送審材料：`instagram_business_basic` + `instagram_business_manage_messages` **同案送審**，use case 以「AI 對話練習教練」框架撰寫，錄製操作影片

> Development Mode 下，App 可與具有 app role（admin/developer/tester）的帳號正常收發訊息 → **不必等審核通過即可開發與測試完整流程**。

### Phase 1 — 骨架與通道打通
- FastAPI webhook endpoint + 簽章驗證 + 多角色路由
- Postgres schema（上述草案）+ Redis
- **`LLMProvider` 抽象介面**（三條路徑各自可獨立設定模型）
- 開發期用 Cloudflare Tunnel / ngrok 對外暴露 HTTPS（Meta webhook 需公開 HTTPS）
- 目標：在測試帳號上完成一次「收訊 → 固定回覆 → 存 DB」

### Phase 2 — 角色對話
- 人設卡結構設計 + system prompt 模板 + prompt caching
- 對話開頭 AI 揭露訊息（政策要求）
- 滾動對話窗 + 摘要壓縮
- typing indicator + 擬真延遲節奏
- 訊息 1000 bytes 切分邏輯
- **即時訊號標記**：依 §3.4.6 偵測地雷／句點／亮點並寫入 `realtime_signals`（報告生成的資料來源，不可延後）
- **實測 200/hr 門檻是否成立**

### Phase 3 — 教練回饋
- 靜默 25 分鐘 session 結束判定（FastAPI 背景 loop 掃 Postgres，不用 n8n）
- 邀請訊息設計：**先問要不要，不直接推送長報告**（省成本 + 降低打擾感 + 點擊即重置 24h 視窗）
- Quick Reply 邀請 + Persistent Menu + Ice Breakers 設定
- postback webhook 處理 + 視窗重開
- 顧問身分 prompt + 固定抬頭模板（依 §3.4.1、§3.4.2）
- 報告生成（依 §3.4.3 結構；先用免費模型，另用高階模型跑 20–30 份建立品質基準線）+ 多則訊息發送

### Phase 4 — 安全與後台
- 旁路即時風險分類器（小模型即可）
- 安全事件升級路徑與真人介面
- 年齡把關
- React 後台：角色管理、對話檢視、安全事件佇列

### 延後（不在 MVP）
輪廓萃取、想想交友配對比對、角色克隆。這三項依賴前期累積的對話量，在使用者基數不足時無法驗證。但 Phase 1 的 schema 需預留 `user_profile` 與 consent 欄位，避免日後遷移。

## 五、驗證方式

| 階段 | 驗證動作 |
|---|---|
| Phase 1 | 從真實 IG 手機 App 對測試角色帳號發訊，確認 webhook 收到事件、簽章驗證通過、DB 有紀錄、回覆送達 |
| Phase 2 | 連續對話 30 則，檢查人設一致性、回覆延遲 <5 秒、中文未被 1000 bytes 截斷；**壓測驗證每小時實際可送訊息數** |
| Phase 3 | 模擬靜默 25 分鐘 → 確認邀請訊息送達；點擊 Quick Reply 與 Persistent Menu 兩條路徑皆能觸發 postback 並成功回傳報告；**在桌面版 IG 驗證 Quick Reply 路徑可用** |
| Phase 3 | 刻意讓對話靜置超過 24h，確認系統正確拒發並轉為待送狀態 |
| Phase 4 | 以測試語句觸發自傷／性內容／未成年情境，確認分類器攔截且事件進入後台佇列 |
