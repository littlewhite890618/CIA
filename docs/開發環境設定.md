# 開發環境設定

更新日：2026-10-02（新增 C. Docker 運行）

本文件涵蓋兩條軌道，**可以同時進行**：

| 軌道 | 內容 | 誰做 |
|---|---|---|
| A. Meta 平台設定 | 建帳號、建 App、加測試人員、設 webhook | **人工，只有你能做** |
| B. 本機開發環境 | Python、虛擬環境、tunnel | 已由程式完成大半 |

**C. Docker 運行**是正式對外服務的方式：服務、PostgreSQL、ngrok 一個指令全部啟動。
B 軌道的「主機上直接執行」保留給快速開發與跑測試。從 SQLite 第一次切換到
PostgreSQL 的一次性步驟見 [切換到PostgreSQL.md](切換到PostgreSQL.md)。

> **A 軌道卡住時，B 軌道不會停。** webhook 接收與簽章驗證可用假 payload 先行開發測試，
> 不需等 Meta 帳號就緒。這是排程改為並行的原因。

# A. Meta 平台設定（人工）

## A-1　建立 Meta 開發者帳號

1. 前往 <https://developers.facebook.com>
2. 右上角「開始使用」，以 Facebook 帳號登入
3. 完成手機或 email 驗證
4. 選擇開發者身分（選「其他」即可）

## A-2　建立 App

1. 前往 <https://developers.facebook.com/apps>
2. 「建立應用程式」
3. 填寫應用程式名稱與聯絡 email
4. **使用案例**：勾選「**管理 Instagram 的訊息和內容**」
   （在「商務式訊息」篩選分類下，描述含「回覆 Direct 訊息」）
5. 若後續詢問應用程式類型，選「**商家**」
6. 建立完成後，記下 **應用程式編號**

> **選這個使用案例會自動加好三樣東西**，省下手動設定：
> - Instagram 產品（不用再「新增產品」）
> - `instagram_business_basic` 權限
> - `instagram_business_manage_messages` 權限（收發私訊用）
>
> 選「其他」的話這些都要手動加，多繞好幾步。

**取得 App Secret**：
應用程式後台 → 左側「應用程式設定」→「基本資料」→「應用程式密鑰」→ 點「顯示」

填入 `.env` 的 `META_APP_SECRET`。**不要外流，也不要進版控。**

> ### ⚠️ 這組密鑰**不是**用來驗證 webhook 簽章的（2026-09-08 更正）
>
> Meta 後台有**兩組**編號與密鑰，長得很像但用途不同：
>
> | 位置 | 名稱 | 用途 |
> |---|---|---|
> | 應用程式設定 → 基本資料 | 應用程式編號／密鑰 | Facebook 層級，換 app access token 等 |
> | **Instagram 產品頁 → API 設定** | **Instagram 應用程式編號／密鑰** | **webhook 的 `X-Hub-Signature-256` 用這組簽** |
>
> 用錯的話，**每一筆真實 webhook 都會驗章失敗**，而且極難從症狀反推——
> 因為後台「測試」按鈕送的是假簽章，兩組密鑰都驗不過，無法用來分辨。
> Meta 官方文件完全沒有提到這件事。
>
> Instagram 那組請填入 `.env` 的 `IG_APP_ID` 與 `IG_APP_SECRET`。

## A-3　建立晴晴的 Instagram 專業帳號

1. 用 Instagram App 註冊一個新帳號（建議與個人帳號分開）
2. 設定名稱、大頭貼
3. **簡介必須標註為 AI** —— 這是 Meta 政策要求，例如：
   ```
   我是 AI 對話練習夥伴 🌿
   陪你練習聊天，聊完給你具體建議
   ```
4. 切換為專業帳號：
   `設定與隱私` → `帳號類型與工具` → `切換為專業帳號` → 選 **Creator** 或 **Business**

## A-4　把 IG 帳號連到 App

> A-2 選了 Instagram 使用案例的話，**Instagram 產品已經自動加好了**，
> 直接從左側選單找到它即可，不需要「新增產品」。

1. App 後台 → 左側找到 **Instagram**
2. 選擇 **API setup with Instagram login**（搭配 Instagram 登入的 API 設定）
3. 第一步「**Generate access token**」→ 用晴晴的 IG 帳號登入並授權
4. 產生後會得到：
   - **存取權杖** → 填入 `.env` 的 `IG_ACCESS_TOKEN`
   - **Instagram 帳號編號** → 填入 `.env` 的 `IG_ACCOUNT_ID`

> 介面文字可能因 Meta 改版而不同。找不到時，關鍵字是
> **Instagram** → **API setup** → **access token**。

## A-5　加入測試人員 ⚠️ 這一步解鎖開發，需要「兩個」帳號都加，不是一個

**⚠️ 2026-09-08 更正**：先前版本寫「一般使用者本來就能傳訊息觸發 webhook」，
經查證是錯的。Development Mode 下，**Meta 只會轉發「測試人員」帳號傳來的訊息**，
非測試人員傳的訊息會被靜默忽略——不會報錯，webhook 完全不會被觸發，
你的伺服器連請求都收不到。查證依據：Meta 開發者社群明確指出
「Webhooks are only triggered when direct messages are sent from an
Instagram account designated as a tester」。

**因此需要加入的測試人員其實是兩種不同用途的帳號**：

| 帳號 | 用途 | 何時加入 |
|---|---|---|
| 晴晴的 IG 帳號（例如 baijohnny） | 被 App 管理、實際收發訊息的帳號 | A-4 產生存取權杖之前 |
| **你手機上拿來傳訊息的帳號** | 用來測試「私訊晴晴」的那個使用者帳號 | **同樣要加，否則你傳的訊息 Meta 不會轉發** |

你不可能自己傳訊息給自己，所以這兩個必須是**不同的兩個 IG 帳號**，
而且**都要**加入測試人員名單並各自接受邀請。

### 加入晴晴的帳號（解鎖 A-4）

1. App 後台 → 左側「應用程式角色」→ 新增人員
2. 選「**Instagram 測試人員**」
3. 填入**晴晴的 IG 帳號**使用者名稱，送出邀請
4. 改用**晴晴的帳號**登入 Instagram 網頁版
5. `設定` → `網站許可` → `測試人員邀請` → **接受邀請**
6. 回到 A-4，重新產生存取權杖（這次應該不會再卡角色不足）

### 加入你要用來傳訊息的帳號（解鎖真的收得到訊息）

1. 同樣路徑，再新增一次測試人員
2. 這次填**你手機上實際要拿來私訊晴晴的那個帳號**（不是晴晴自己）
3. 用**那個帳號**登入網頁版接受邀請
4. 之後用該帳號的手機 App 私訊晴晴，webhook 才會真的被觸發

> 兩邊的「接受邀請」都不能漏，各自獨立、互不影響對方。

## A-6　設定 webhook

**此步驟需要先有公開網址，請先完成下方 B-3 的 ngrok 設定。**

1. App 後台 → Instagram 產品頁 → 「**Configure webhooks**」
2. **Callback URL**：填 `https://你的網址/webhook`
3. **Verify Token**：自訂一組字串（例如 `cia_poc_verify_2026`），
   同一組字串也要填進 `.env` 的 `META_WEBHOOK_VERIFY_TOKEN`
4. 點「驗證並儲存」—— 此時 Meta 會打你的 endpoint 做驗證，**服務必須正在執行**
5. 訂閱欄位：勾選 **`messages`** 與 **`messaging_postbacks`**

## A-7　把 App 切換為「上線」模式 ⚠️ 不做的話收不到任何真實訊息

**⚠️ 2026-09-08 更正（實測代價很高的一項）**：先前版本寫
「Development Mode 下，App 可與具備測試人員身分的帳號正常收發訊息」，
**這是錯的**。Meta 後台「設定 Webhooks」區塊自己寫著：

> ⓘ 若要接收 Webhooks，你的應用程式必須為**已發佈狀態**。

開發模式下，即使以下全部正確，**真實私訊一筆都不會被轉發**：
回呼網址已驗證、`messages` 已訂閱、帳號層級 `subscribed_apps` 已訂閱、
收發雙方都是已接受邀請的 Instagram 測試人員。
症狀是「完全靜默」——伺服器連請求都收不到，後台也不會顯示任何錯誤。

網路上大量文章（含多個開發者社群回答）都說開發模式配合測試人員就能收訊息，
**與 Meta 後台的實際行為不符**。以後台文字為準。

### 步驟

1. App 後台 → 最上方「應用程式模式」開關 → 從「開發中」切到「**上線**」
2. 若被擋，依提示補齊 `應用程式設定 → 基本資料` 的欄位
   （最常見缺的是**隱私政策網址**，該網址必須真的可以打開、不能是 404 或轉址到首頁）

### 上線之後仍然安全

切到上線模式**不等於對全世界開放**。未通過 App Review 的權限只有
**Standard Access**，而 Standard Access 的權限**只能作用在具備角色的使用者身上**
（管理員、開發人員、測試人員）。也就是說：

- 陌生人傳訊息給晴晴 → 仍然不會觸發 webhook
- 只有測試人員傳的訊息才會進來

POC 階段這正是我們要的行為，因此**不需要送 App Review、不需要商業驗證**。

# B. 本機開發環境

## B-1　Python 環境（已完成）

```bash
python -m venv .venv
.venv/Scripts/python.exe -m pip install -r requirements.txt
```

已安裝：FastAPI、SQLAlchemy、PyYAML、httpx、pydantic-settings、pytest

## B-2　環境變數

複製範本並填入 A 軌道取得的憑證：

```bash
cp .env.example .env
```

| 變數 | 來源 | 備註 |
|---|---|---|
| `META_APP_SECRET` | A-2 的應用程式密鑰 | 目前程式未使用，保留備用 |
| `META_WEBHOOK_VERIFY_TOKEN` | A-6 自訂，兩邊要一致 | |
| `IG_APP_ID` | Instagram 產品頁 → API 設定 | |
| **`IG_APP_SECRET`** | **同上，Instagram 專屬密鑰** | **webhook 驗章用的是這組**（見 A-2 的警告框） |
| `IG_ACCESS_TOKEN` | A-4 產生的存取權杖 | |
| `IG_ACCOUNT_ID` | A-4 的 Instagram 帳號編號 | 須與 webhook payload 的 `entry[].id` 相同 |
| `GEMINI_API_KEY` | <https://aistudio.google.com/apikey> 免費取得 | |

> **憑證未填不會擋住啟動。** 服務會記錄警告並繼續執行，
> 讓你能用假 payload 測試 webhook 邏輯。

## B-3　ngrok（對外公開網址）

你的程式跑在自己電腦上，網址是 `localhost:8000`，Meta 從外面打不進來。
tunnel 的作用是給你一個公開網址，把流量轉進本機。

**為什麼用 ngrok 而非 Cloudflare Tunnel**：

| | ngrok 免費版 | Cloudflare Quick Tunnel |
|---|---|---|
| 固定網址 | ✅ 每個帳號 1 個免費固定網域 | ❌ 每次重啟隨機更換 |
| 請求檢視 | ✅ 可看完整 payload | ❌ 無 |
| **請求重播** | ✅ **可重送 Meta 的封包** | ❌ 無 |

**請求重播對 webhook 開發特別有價值** —— 拿到一次真實的 Meta 封包後，
可以重複重播來除錯，不必每次都拿手機傳新訊息。

**設定步驟**：

1. 註冊 <https://dashboard.ngrok.com/signup>（免費）
2. 下載並安裝 ngrok
3. 綁定帳號：
   ```bash
   ngrok config add-authtoken 你的_token
   ```
4. Dashboard → **Domains** → 取得你的免費固定網域
   （形如 `xxxx-xxxx.ngrok-free.app`）
5. 啟動：
   ```bash
   ngrok http 8000 --url=你的固定網域
   ```
   （ngrok 3 新版改用 `--url`，舊的 `--domain` 寫法已不在說明中列出）
6. 把 `https://你的固定網域/webhook` 填進 A-6 的 Callback URL

> **請求檢視介面**：ngrok 啟動後開 <http://localhost:4040>，
> 可看到每一筆進來的請求，並可重播。

## B-4　啟動服務（主機上直接執行，不用 Docker）

```bash
.venv/Scripts/python.exe -m uvicorn app.main:app --reload --port 8000
```

`DATABASE_URL` 指向哪裡，服務就用哪個資料庫：

- **指向 Docker 裡的 Postgres**（`127.0.0.1:15432`）：要先 `docker compose up -d db`，
  並執行過 `.venv/Scripts/alembic.exe upgrade head`。結構不是最新版時服務會拒絕啟動
- **指向 SQLite**（如 `sqlite:///./data/local.db`）：不需要 Docker，全新的檔案會自動建表

> ⚠️ 不要和 C 軌道的容器同時跑：兩邊都用 8000 埠，而且只能有一份服務在處理 webhook。

## B-5　執行測試

```bash
.venv/Scripts/python.exe -m pytest
```

測試一律使用 SQLite，不需要 Docker。另有一組 Postgres 專用測試（標記 `postgres`），
只在設定 `TEST_DATABASE_URL` 時執行，用法見 `tests/test_postgres_smoke.py` 開頭。

# C. Docker 運行

**前提**：Docker Desktop 已啟動，`.env` 已依 `.env.example` 填好 `POSTGRES_*`、
`NGROK_AUTHTOKEN`、`NGROK_DOMAIN`。

## C-1　三個服務

| 服務 | 做什麼 | 主機上怎麼連 |
|---|---|---|
| `db` | PostgreSQL 16，資料存在 Docker volume `cia_pgdata` | `127.0.0.1:15432`（不是 5432——這台桌機原生的 PostgreSQL 已佔用 5432／5433） |
| `app` | 本專案的服務，固定只跑一份 | `http://127.0.0.1:8000/health` |
| `ngrok` | 用固定網域把 Meta 的 webhook 轉進 `app` | 請求檢視介面 <http://127.0.0.1:4040> |

> ⚠️ **主機上的 ngrok 要先關掉。** 免費版同一時間只允許一個連線，
> 主機上的還開著，容器裡的就會連線失敗。

## C-2　正式模式（平常就用這個）

```bash
docker compose up -d          # 啟動全部；也用來「切回正式模式」
docker compose ps             # 三個服務都要顯示 healthy／running
docker compose logs -f app    # 看服務的 log
docker compose down           # 停止全部（資料保留）
```

- 使用映像檔裡的程式碼，**本機改程式不會影響正在跑的服務**
- 改了程式要上線：`docker compose up -d --build app`
- 改了人設卡（`app/personas/cards/`）：`docker compose restart app` 即可，不必重建
- 人設卡缺欄位時 `app` 會啟動失敗並重複重啟，`docker compose logs app` 會指出缺哪個欄位

> ⚠️ **不要執行 `docker compose down -v`**——`-v` 會連資料庫一起刪掉，目前沒有備份。

## C-3　開發模式（改程式時用）

```bash
docker compose -f docker-compose.yml -f docker-compose.dev.yml up -d
```

- 本機的 `app/`、`alembic/`、`scripts/` 直接掛進容器，**存檔後服務自動重載**，不必重建
- 存到有錯的程式碼：重載失敗、log 會出現錯誤；修好再存檔就恢復，不必重啟容器
- 新增 Alembic revision：`docker compose restart app` 時自動套用
- 改了 `requirements.txt`：仍要重建 `docker compose build app`（套件裝在映像檔裡）
- 開發模式與正式模式**共用同一個資料庫**，開發時的測試訊息會寫進正式資料

> ⚠️ **對外開放後，開發模式只在維護時段使用。** 開發模式下每次存檔都會立刻影響
> 正在聊天的使用者，存到一半的檔案也會讓服務中斷。用完記得切回正式模式：
> `docker compose up -d`

**確認現在是哪種模式**：

```bash
docker compose ps --format "{{.Service}}: {{.Command}}"
```

`app` 的指令裡有 `--reload` 就是開發模式，沒有就是正式模式。

# 每日開發流程

**用 Docker（建議）**：

```
1. 切到開發模式：  docker compose -f docker-compose.yml -f docker-compose.dev.yml up -d
2. 用手機 IG 私訊晴晴
3. 在 http://127.0.0.1:4040 看 Meta 送來什麼
4. 改程式，存檔後自動重載
5. 在 ngrok 介面點 Replay 重送剛才的請求，不用再傳一次訊息
6. 做完切回正式模式：docker compose up -d --build app
```

**不用 Docker**（先 `docker compose down` 停掉容器）：

```
1. 開一個終端機跑 ngrok：   ngrok http 8000 --url=你的固定網域
2. 開另一個跑服務：          uvicorn app.main:app --reload --port 8000
3. 用手機 IG 私訊晴晴
4. 在 http://localhost:4040 看 Meta 送來什麼
5. 改程式（--reload 會自動重啟）
6. 在 ngrok 介面點 Replay 重送剛才的請求，不用再傳一次訊息
```

> **卡住時的除錯順序**（依 9/8 實戰經驗整理）：
> 1. `localhost:4040` 有沒有 POST 進來？沒有 → 問題在 Meta 端，往下看
> 2. App 是不是「上線」模式？（A-7，最容易漏）
> 3. 收發雙方是否都已**接受**測試人員邀請？（列在名單上 ≠ 已接受）
> 4. 私訊的對象是不是 `.env` 裡 `IG_ACCOUNT_ID` 對應的那個帳號？
