## Context

動機見 `proposal.md` — Why。本 change 的特點是**零件幾乎都已存在，缺的是串接**：

- `coach_reports` 表已建（session_id／generated_at／delivered_at／content），content 的註解已載明五段結構
- `sessions.invite_sent` 已存在，且 `repository.find_silent_sessions()` 已將它納入查詢條件——這個旗標當初就是為了防止輪詢重複發邀請而設
- 靜默輪詢迴圈（`_silence_poll_loop`）已運作，會把逾門檻的 session 標記為結束
- postback 已能解析，`_handle_postback()` 會重置訊息視窗但**只把 payload 記進日誌**，沒有後續動作
- 訊號偵測已逐則落庫並帶有 `signal_status`，失敗者可由 `scripts/rerun_signals.py` 重跑
- 發訊管線（訊息切分、視窗檢查、速率配額、順序保證）已完成且經真機驗證
- `llm-provider` 的 coaching 路徑已定義但**從未被使用**，本 change 是它的第一個消費端

## Goals / Non-Goals

**Goals:**

- 讓訊號轉化為使用者看得懂的回饋，完成 Phase 1 完成定義中缺少的一段
- 在使用者同意的前提下才生成與送出分析
- 模型呼叫成本可控：一份報告只生成一次，送達失敗不重複計費

**Non-Goals:**

- 不做配對結果通知（M9 v3），該部分受 24 小時視窗限制且需備援路徑，屬 Phase 3
- 不改動訊號偵測的判定準則（`realtime-signals` 既有需求不變）
- 不做報告的網頁版或歷史查閱介面，報告經由對話送達
- 不處理「使用者要求刪除報告」等資料權利流程，屬合規範圍另行處理

## Decisions

**0. 邀請按鈕用 Button Template（postback），不是 Quick Reply**

曾一度改用 Quick Reply，**2026-09-23 真機實測推翻**，最終回到 tasks 原本
寫的 postback 路線。完整經過留在這裡，因為這個坑從症狀完全看不出來：

- 先前依 `docs/技術可行性與架構規劃.md` §1.2「Quick Replies 手機＋桌面皆可、
  Persistent Menu／Ice Breaker 僅手機版」的判斷，選了 Quick Reply
- 實測結果：`message.quick_replies` 送出後 **API 回 200、拿得到 `message_id`、
  訊息也真的送達，但手機 App 與桌面瀏覽器都沒有任何按鈕**。Graph API 對
  不支援的欄位默默忽略，不報錯，因此「以為成功了其實沒有」
- 同帳號同端點改送 Button Template（`attachment.type=template` /
  `template_type=button` / `buttons[].type=postback`）→ 按鈕正常顯示，點擊
  觸發 `messaging_postbacks`，payload 正確（log：`收到 postback |
  payload='DIAG_BT_CLEAN'`）
- 該研究文件的判斷已於同日訂正，推測是把 Messenger 平台的 Quick Reply
  （確實支援桌面）與 Instagram 平台的搞混

因此最終實作：
- 送出用 `InstagramClient.send_button_template()`；`MessageSender` 對應的是
  `send_button_template()`。`_send_one()` 重構成接受可替換的 `send_fn`，
  讓按鈕訊息沿用既有的配額／重試／視窗檢查，不必重寫一份
- 觸發邏輯在 `_handle_postback()`（既有的 `PostbackEvent` 分支），
  `_parse_one()` 不需要任何改動——這正是 tasks 4.1 原本的寫法

**連帶修掉一個真實 bug**：`_handle_postback()` 從不落庫任何訊息，導致點擊
按鈕新建的 session 對 `MessageSender` 的「未互動使用者阻擋」（4.4）而言
形同陌生人，報告會被判 `no_inbound_interaction` 而送不出去。現在會補記一筆
入站訊息（內容用按鈕文字），維持「任何要收到回覆的 session 都至少有一則
入站訊息」這個既有不變式，而不是去放寬 `MessageSender` 的共用檢查——後者
會影響所有發訊路徑。

**尚未驗證**：桌面版瀏覽器是否顯示 Button Template。若同樣不顯示，代表桌面
使用者沒有任何可點的元件，需要另設路徑（見研究文件的訂正段）。

**1. 邀請與生成分離，使用者點擊後才生成**

不在 session 結束時就把報告生成好等著。理由有二：一是使用者未必想看，先生成等於為沒人要的內容付模型費用；二是主動推送分析會讓使用者有被評價的感覺，與產品「陪聊」的定位衝突。

*替代方案*：結束即生成並直接送出。實作較簡單，但成本浪費且體驗較差。

**2. 生成觸發由 postback payload 決定，不靠訊息文字比對**

`_handle_postback()` 已能取得 payload，以結構化的 payload 值辨識「使用者要看報告」與所屬 session，比解析使用者輸入的文字可靠。

*替代方案*：讓使用者回覆特定關鍵字。會與正常聊天內容混淆，且無法攜帶 session 識別。

**3. 「已生成未送達」是獨立狀態，不與「生成失敗」混為一談**

`coach_reports` 已將 `generated_at` 與 `delivered_at` 分為兩欄，其註解明言「NULL 表示已生成但未送達，可據以補送與追成本」。設計沿用此意圖：送達失敗只重試送出，不重新呼叫模型。

**4. 報告走 coaching 路徑，且可用與對話不同的模型**

報告生成不在使用者等待回覆的即時路徑上，對延遲的容忍度遠高於對話。對話路徑因此選了快的 `gemini-3.6-flash`（3.6 秒），但報告品質的重要性高於速度，應評估改用推理能力較強的模型。此決定可經設定調整，不需改動程式。

**5. 互動過少的對話不邀請**

只有兩三則往返的對話產不出有意義的回饋，硬生成只會得到空泛內容，損害產品信任感。設下限並記錄略過原因，具體門檻值可設定。

**6. 視窗逾期時不呼叫平台 API**

與既有的發訊設計一致（`ig-messaging` 已有此需求且經真機驗證，逾期呼叫會得到 `error_subcode 2534022`）。邀請與報告都沿用同一條發訊管線，自動繼承此行為，不另寫檢查。

**8. 送達失敗的補救只由使用者再次點擊觸發，不因任何新訊息自動補送（2026-09-24 產品決策修訂）**

原設計是：使用者傳送任何一則新訊息（不限於再次點擊邀請）重開視窗時，系統背景自動補送所有「已生成未送達」的報告。真機測試驗證這個行為技術上可行後，使用者提出實際體感疑慮：報告與那則新訊息的內容通常無關，使用者可能早已忘記自己先前點過邀請，收到報告會顯得突兀、莫名其妙。

改為：只有使用者**明確再次點擊**查看回饋的按鈕（Button Template 不會消失，任何時候都能再點）才會嘗試補送，仍然不重新呼叫模型（沿用決策 3 的既有內容）。移除了 `repo.undelivered_reports_for_link()` 與 `_handle_message()` 裡逐則訊息掃描待補送報告的邏輯。

*替代方案*：保留自動補送，但在送出時加一句前言（例如「補上你之前想看的那次對話回饋：」）緩解唐突感。使用者評估後選擇直接移除此機制，而非加前言緩解——判斷是「不主動」比「主動但先講清楚」更貼近產品「陪聊」的定位，且實作更簡單。

*已知限制*：若使用者從未再點擊按鈕，一份送達失敗的報告會永遠卡在「已生成未送達」，沒有任何自動機制會再嘗試。這是刻意的取捨，不是遺漏。

## Risks / Trade-offs

**24 小時視窗使部分報告永遠送不出去** → 使用者靜默結束的時間點若已接近視窗尾端，邀請可能發不出去；即使發出，使用者隔天才點擊時視窗也已逾期。緩解：報告保留為已生成未送達，待使用者**再次點擊查看回饋**（決策 8）時補送。無法完全解決，這是平台的硬限制；且若使用者從此不再點擊，該報告將永久停留在未送達狀態。

**訊號偵測失敗會讓報告無法生成** → 訊號是報告的唯一資料來源。緩解：不以不完整訊號硬生成（那會產出誤導使用者的評價），改為保留可重新生成的狀態，配合既有的 `scripts/rerun_signals.py` 補齊後再產。

**教練報告的內容品質難以自動驗證** → 五段結構可用程式檢查，但「建議是否中肯」只能人工判斷。緩解：端對端驗證需包含人工閱讀實際報告，不能只看測試綠燈。

**首次啟用 coaching 路徑，額度消耗增加**（**2026-09-29 實測後解除**）→ 原本擔心對話路徑的 Gemini 免費額度已知偏緊（RPD 有限且非按日曆日重置），報告生成會再吃一份額度。實測 4 次真實呼叫平均 806 tokens、頻率低（一場對話最多一份報告，且需使用者主動點擊才生成），對照免費層 RPD 500／TPM 250K 餘裕充足，不構成風險。真正的額度壓力在 dialog 路徑——單次對話回覆實測已達 1,440–2,714 tokens 且隨對話長度持續增長，遠高於報告生成。必要時報告路徑仍可改用不同金鑰或供應商，`llm-provider` 的抽換設計已支援。

## Migration Plan

1. **補資料欄位**——`coach_reports` 的失敗原因欄位，沿用既有的啟動補欄位機制
2. **邀請**——靜默輪詢在標記結束後送出邀請；此時點擊按鈕尚無作用
3. **生成**——postback 觸發，報告內容落庫但先不送出，可先以日誌檢視內容品質
4. **送達**——接上既有發訊管線
5. **補救路徑**——已生成未送達的補送

**回滾**：各階段獨立。邀請發送可由設定關閉，關閉後系統行為回到本 change 之前（session 正常結束，只是不邀請）。
