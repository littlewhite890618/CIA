## Context

專案為全新建置，無既有程式碼。動機見 `proposal.md` - Why；平台限制的完整查證見 `docs/技術可行性與架構規劃.md`；人設卡的結構參考範例見 `docs/人設卡草案-晴晴.yaml`。

塑造本設計的三項外部約束：

1. **Meta webhook 要求快速回應**，逾時會重送事件。但角色回覆需要語言模型呼叫加上刻意的擬真延遲（依人設可達數十秒），兩者時間尺度差距懸殊。
2. **24 小時訊息視窗與發訊速率**是硬性平台規則，違反會導致 API 錯誤或帳號受限，必須在系統層強制，不能交由呼叫端自律。
3. **MVP 使用免費模型**，其速率上限低且不穩定，供應層必須把失敗視為常態而非例外。

團隊既有技術背景為 Python、Postgres、React、Docker Compose。

## Goals / Non-Goals

**Goals:**

- 平台規則（視窗、速率、長度）由通道層統一強制，上層功能不需各自處理
- 人設卡的資料結構與提示渲染分離，使新增角色不需修改程式碼
- 語言模型供應商可抽換，且失敗不會中斷對話
- 教練回饋所需的行為訊號在 session 結束時即落庫
- 在 Meta App Review 通過前即可於 Development Mode 完整開發與測試

**Non-Goals:**

- 不建立營運後台（Phase 4）
- 不做安全護欄與風險升級（Phase 4）
- 不做水平擴展與多實例部署；MVP 為單實例
- 不做多角色的負載平衡；MVP 僅一個角色
- 不引入 n8n

## Decisions

### 1. Webhook 採「同步落庫、非同步回覆」

**決定**：webhook handler 只做驗章、解析、去重、落庫，隨即回應 200；角色回覆在背景任務中產生與送出。

**理由**：Meta 對 webhook 有回應時限，而擬真延遲本身就要求回覆晚於收訊數秒到數十秒。若在 handler 內同步完成，必然逾時並觸發 Meta 重送，造成重複回覆。

**替代方案**：在 handler 內同步處理並取消擬真延遲 —— 放棄擬真節奏會直接損害產品的核心體驗，不可接受。

**MVP 實作**：使用 FastAPI 的背景任務，不引入 Celery。訊息在回應 200 前已落庫，因此即使行程中斷，重啟後仍可由資料庫找出未回覆的入站訊息進行補救。待需要多實例部署時再導入獨立的工作佇列。

### 2. 平台規則的真相來源放在 Postgres，Redis 僅為快取

**決定**：`sessions.window_expires_at` 與訊息紀錄以 Postgres 為真相；Redis 存放熱點快取與發訊配額計數。

**理由**：視窗到期時間一旦遺失，系統會誤判而發出被平台拒絕的訊息。Redis 重啟即空，不適合承載此類不可重建的狀態。

**例外**：發訊配額計數以 Redis 的滾動計數實作，重啟後歸零可接受 —— 低估用量只會讓發訊更保守，不會違反平台規則。同時將實際觸發速率限制的時機與數量寫入 `rate_budget` 表，作為驗證 200 則/小時假設的觀測資料。

### 3. 靜默判定採背景輪詢，不用排程工具、不用 Redis TTL

**決定**：以單一背景迴圈定期掃描 `sessions`，找出最後活動時間超過門檻且尚未標記結束的 session。

**理由**：Redis 的過期事件通知不保證送達，且重啟後遺失；引入 n8n 或 cron 則多一個元件與一層跨系統除錯。輪詢的狀態完全落在 Postgres，重啟後自動恢復，且此判定對延遲不敏感（門檻本身以分鐘計）。

### 4. 人設卡：YAML 檔 + 結構驗證 + 提示模板

**決定**：人設卡以 YAML 檔存放於程式碼庫，載入時經結構驗證後，透過模板渲染為 system prompt。資料庫的 `personas` 表先建立但 MVP 不作為來源。

**理由**：MVP 僅一個角色，且初期人設調校極為頻繁。改檔案比操作後台表單快，且版本控制能呈現「改了什麼、效果如何」。資料表先建立可避免日後接入後台時的資料遷移。

**關鍵結構**：人設卡分為 `給模型的`（identity/background/personality/language_style/boundaries）與 `runtime`（回覆延遲、拆分機率、輸入提示）。後者由程式執行，不進入提示 —— 指示模型「你要慢慢回」無效，送出時機只有程式能控制。

**驗證**：載入時強制檢查必要欄位，缺漏則啟動失敗。這是維持多角色品質下限的機制，不可降級為警告。

### 5. LLMProvider 介面按用途分路徑，而非按供應商

**決定**：以「對話生成」「即時分析」「教練回饋」三條具名路徑作為設定單位，每條路徑各自繫結供應商與模型。

**理由**：三條路徑對延遲、成本與品質的要求截然不同 —— 對話要快、分析要便宜、回饋要準。按路徑設定可各自最佳化，也讓「用免費模型跑對話、用高階模型建立回饋品質基準線」這種混用成為設定問題而非改碼問題。

**替代方案**：單一全域模型設定 —— 無法表達上述差異，且會迫使三者遷就最嚴格的那個需求。

### 6. 訊號分析於 session 結束後一次進行，且失敗不影響對話

**決定**：訊號分析在 session 結束時，以背景任務對整段對話呼叫一次模型，逐則標記訊號。不在對話進行中逐則分析。

**理由**：訊號分析是為了「今晚的報告」，不是為了「這一則回覆」，本質上可容忍延遲與失敗。報告本就在 session 結束後才產生，逐則即時分析沒有額外收益，卻會讓模型呼叫量翻倍（每則使用者訊息多一次），壓縮免費額度與發訊配額的餘裕。一次看完整段對話，也更能判斷跨訊息的模式（連續只講自己、查戶口式連問、連發封閉式問題）。

**替代方案**：逐則分析、與回覆並行（原決定）—— 呼叫量翻倍，且每次只看得到最近幾則，跨訊息模式判斷較差。唯一優勢是能當下反應，但那是 Phase 4 安全護欄的需求，應由獨立的風險分類器處理，不與教練訊號共用。

**代價**：單次失敗會讓整場 session 沒有訊號。以記錄失敗事件並可事後重跑的方式承擔。長 session 的輸入較長，POC 規模（30 則上下）不構成問題。

> 2026-09-22 修訂：由「逐則並行」改為「session 結束後一次分析」。

### 7. 使用者以 username 歸戶，IGSID 存於中介表

**決定**：`users` 以 Instagram username 為跨角色識別鍵，`user_persona_links` 保存每個角色帳號範圍內的 IGSID。

**理由**：IGSID 的範圍是單一專業帳號，同一人與不同角色互動會得到不同 ID。若直接以 IGSID 作為使用者主鍵，使用者換角色即等同輪廓歸零，會使後續的輪廓累積失效。

**取捨**：username 可被使用者變更，非永久識別碼。MVP 接受此限制；跨角色關聯屬個資處理，需於服務條款揭露。

### 8. 訊息切分優先在語意邊界

**決定**：切分順序為段落、句末標點、逗號，最後才依字元邊界硬切。

**理由**：1000 bytes 上限下中文約 330 字，機械切分會把句子從中間斬斷，嚴重破壞擬真感。硬切僅作為保底，且必須落在完整字元邊界以避免亂碼。

### 9. 事件去重以平台訊息識別碼為準

**決定**：`messages` 對平台訊息識別碼建立唯一索引，重複事件於落庫階段即被擋下。

**理由**：Meta 在未即時收到 200 時會重送。若無去重，一則使用者訊息可能觸發多次回覆與多次模型呼叫。

## Risks / Trade-offs

- **每小時 200 則的發訊上限未經官方確認** → 配額設為可調參數，`rate_budget` 表作為觀測資料來源。實測原為本 change 的 9.7，2026-10-12 移至 `add-persona-authoring-console` 任務 11（2026-10-15 重新編號為任務 9）
- **免費模型的繁中語感不足，出現翻譯腔或 AI 味** → 供應層按路徑抽換，可在不改業務邏輯下更換模型；驗收時將語感列為明確檢查項
- **免費模型的速率上限低，對話中途失敗** → 供應層強制實作退避重試與人設內的降級回應；失敗不得暴露系統錯誤訊息給使用者
- **背景任務隨行程中斷而遺失** → 入站訊息在回應 200 前已落庫，重啟後可據以補救；待需要多實例時再導入獨立佇列
- **擬真延遲期間使用者又發訊，導致回覆已不合時宜** → 以每對話的處理標記合併或取消待送回覆
- **Meta App Review 尚未通過** → 全程於 Development Mode 開發，App 可與具備 app role 的帳號正常收發訊息，不阻塞本 change
- **本 change 交付後系統可對話但無安全護欄** → 明確門檻：Phase 4 完成前不得對外開放真實使用者。首個角色主打「剛受挫、需要被安撫」族群，情緒風險事件機率高於一般，此門檻不可放寬

## Migration Plan

無既有系統需遷移。部署順序：

1. Docker Compose 起 Postgres 與 Redis
2. 以資料庫遷移工具建立 schema（`coach_reports`、`safety_events` 一併建立，本 change 不使用）
3. 設定 Meta App 的 webhook verify token 與 app secret
4. 以 Cloudflare Tunnel 或 ngrok 將本機服務暴露為公開 HTTPS，登錄至 Meta App 的 webhook 設定
5. 於 Development Mode 下以具備 app role 的 Instagram 帳號進行端對端驗證

回滾：移除 Meta App 的 webhook 訂閱即可停止所有入站流量。資料庫可保留，無破壞性變更。
