## Context

動機見 proposal.md。與實作相關的現況：

- 對話靜默 25 分鐘即結束（`_run_silence_pass` → `_close_session_and_analyze`），依序做話題萃取、訊號偵測，最後直接以 Button Template 送出邀請（`_send_coach_invite`）。使用者點按鈕觸發 postback，才產生報告（`generate_report`）並以私訊文字送出。報告存在 `coach_reports`，每段對話一列
- 發訊一律經 `MessageSender`，送出前檢查「有沒有互動過」與 24 小時視窗（`session.window_expires_at`，每則使用者訊息更新為 +24 小時）
- 設定連結：無狀態 HMAC 簽章 token（`app/auth/settings_link.py`，簽章時帶用途前綴），加上「第一個打開的瀏覽器才算數」的登記表 `settings_link_claims` 與 cookie（`app/auth/settings_claim.py`）。只有 API 登記，頁面本身不登記，避免被 IG 的預覽機器人用掉
- 前端是一個 React（Vite）專案，目前只有設定頁，由 FastAPI 送出打包成品
- 給模型的提示中沒有任何「使用繁體中文」的要求
- Gemini 免費額度是目前的承載瓶頸（每分鐘 15 次）

## Goals / Non-Goals

**Goals:**

- 回饋在 Instagram 手機版與網頁版都看得到
- 凌晨 04:00 的送出在 24 小時視窗內一定送得到，服務在 04:00 剛好停機也能補送
- 沿用設定連結已驗證過的簽章與單一瀏覽器機制，不另起一套

**Non-Goals:**

- 不改變對話結束的判定、話題萃取、訊號偵測、長對話摘要的時機
- 不改報告的段落與內容規則（教練設定的套用照舊）
- 不做推播通知或 email
- 回饋頁不做編輯或互動，只呈現

## Decisions

**1. 新增「每日回饋」紀錄，場次指向它**

新表 `coach_digests`：一列代表一則送出的回饋訊息（所屬的使用者連結、建立時刻、送出時刻、未能送出的原因）。`sessions` 新增 `coach_digest_id`（可為 NULL）。

- 「至多送一次」以「`coach_digest_id` 已有值」判定，而不是比對時間區間：服務停機錯過 04:00 時，下一次執行自然會把沒送過的撈出來
- 報告仍是每段對話一列，存在 `coach_reports`，不改結構。頁面依 digest 撈出它的場次與各自的報告
- 舊的 `invite_sent`／`invite_skip_reason` 保留不刪，作為歷史；已標記 `invite_sent` 的舊對話不列入每日送出

*替代方案*：把 digest 資訊塞進 `coach_reports`。但報告要等打開連結才產生，送出當下還沒有報告列可以掛，不合適。

**2. 每日排程：行程內的迴圈，算出下一個 04:00 再睡**

與現有的靜默輪詢同一種做法（單一 worker，見 Dockerfile 的 `--workers 1`）。時刻與時區做成設定（預設 `04:00`、`Asia/Taipei`）。

- 每次執行：找出「已結束、`coach_digest_id` 為空、未曾以舊按鈕邀請、互動達下限」的場次，依使用者連結分組，每組建立一份 digest 並送出
- **啟動時補跑**：若上一次應執行的 04:00 已過、而那次沒有執行紀錄，啟動後立刻跑一次。24 小時視窗的檢查交給 `MessageSender`，送不到就記原因
- 「下一個 04:00」的語意由「沒送過的都撈」自然達成：凌晨 02:00 結束的對話，在 04:00 那次就會被撈到
- 互動未達下限的場次也寫上略過原因並標記已處理，避免每天重複掃描

*替代方案*：作業系統的 cron 或另一個容器。多一個要部署、監看的元件，目前規模不需要。

**3. 回饋訊息掛在哪一段對話上送出**

用這位使用者**最新的一段對話**作為送出的 session：它的 `window_expires_at` 就是最後一則使用者訊息 +24 小時，正好是平台的視窗。訊息以新的 `SystemMessageKind`（`coach_digest`）標記，沿用既有的過濾，不進入對話上下文、話題萃取與訊號偵測。若使用者在 04:00 正在聊天，這則訊息會出現在進行中的對話裡，但不影響晴晴的回覆。

**4. 回饋連結：同一套簽章，用途前綴不同**

把 `settings_link.py` 的簽章抽成可帶用途參數的共用函式：設定連結用 `settings-link:v1`，回饋連結用 `coach-report:v1`，綁定 `digest_id` 與到期時間（7 天，可調）。用途前綴不同，兩種 token 互相不能冒用。

單一瀏覽器登記沿用 `settings_link_claims` 表（以 token 雜湊為鍵，兩種 token 不會撞），cookie 另取名、路徑限定在 `/api/report`，與設定頁的 cookie 互不干擾。頁面本身（`/report`）不登記。

**5. 打開連結才產生報告，前端逐段觸發**

- `GET /api/report?t=` 回傳 digest 的場次清單與各段狀態（已有報告、可產生、分析未完成、產生失敗）。只讀，不呼叫模型
- `POST /api/report/sessions/{id}/generate?t=` 產生單一段的報告，並確認這段屬於這個 digest
- 前端拿到清單後，對「可產生」的段落**一段一段依序**呼叫，邊產生邊顯示。依序而非同時，是為了不在同一秒對 Gemini 打出好幾個請求（每分鐘 15 次的限制）
- 同一段同時被觸發兩次（例如快速重新整理）：以既有的 `get_or_create_coach_report` 與「已產生就直接回傳」防止重複呼叫模型
- 報告第一次被回傳給頁面時寫入 `delivered_at`，語意改為「第一次被看到的時刻」

*替代方案*：一個 GET 產生全部段落再回傳。三段就要等 15～30 秒才有畫面，且容易逾時。

**6. 舊按鈕的處理**

`COACH_REPORT_VIEW:` postback 仍會進來（使用者手上有舊訊息）。改為：為這段對話建立（或沿用已存在的）digest，回覆一則附連結的訊息。不再在私訊中送報告內容。

**7. 繁體中文：提示＋程式轉換，只轉輸出**

- 晴晴、教練報告、長對話摘要的提示都加上「使用繁體中文與台灣慣用語」
- 程式端以 OpenCC 的 `s2tw` 轉換（只轉字形與台灣異體字，不轉詞彙），套用在：晴晴的回覆送出前、報告解析後保存前、摘要保存前
- 不用 `s2twp`（會把「信息」改成「資訊」這類詞彙）：已經是繁體的句子可能被改寫用詞，違反「原本就是繁體的內容不被改寫」的規格情境
- 使用者傳來的訊息、訊號偵測的判定原因（含使用者原句）都不轉
- 套件選純 Python 實作的版本，Docker 映像檔不需額外的系統函式庫

**8. 關鍵字改為「芝麻開門」**

只改 `SETTINGS_KEYWORD` 的預設值；比對方式不變（去掉前後空白後完全相同）。揭露提示與設定連結的訊息原本就讀這個設定，會自動跟著改。設定頁前端寫死的「傳一次『設定』」改成由 API 回傳關鍵字顯示，避免下次改關鍵字又要改前端。

**9. 回饋頁的視覺**

沿用設定頁的設計系統（白底、藍色文字、同一套字體與元件），作為同一個 React 專案的第二個頁面。這是唯讀的閱讀型頁面，以手機寬度為主。連結預覽卡片沿用晴晴的照片，標題「晴晴的聊天回饋」。

與頁面有關的工作一律透過 impeccable skill 進行（2026-10-21 使用者要求）：先載入 impeccable 的專案脈絡，依 PRODUCT.md 與設定頁的 surface brief 為回饋頁建立 surface brief，完成後跑 detect 並交給 finish reviewer 審查。設定頁與回饋頁完成後，以 impeccable document 產生 DESIGN.md，讓之後的頁面有一致的依據。

**10. 開場改為不含「AI」的問候（使用者決定）**

開場文字改為「嗨，我是晴晴，戀愛顧問🌿」，拿掉「AI」「不是真人唷」與「設定」提示。出現時機不變（`should_disclose`：新對話開頭、長時間中斷後），程式上只換文字、拿掉提示參數。設定連結的回覆在新對話時同樣以這行開頭。

2026-10-21 使用者在被告知風險後明確決定採用，屬產品決策，實作時照做、不再反覆提出。已知風險：
- Meta Messenger 平台政策要求自動化對話在開頭揭露為自動服務（docs/技術可行性與架構規劃.md §1.4，只寫在個人簡介不夠）。若被檢舉或抽查，受影響的是唯一的帳號
- 晴晴的人設擬真，使用者可能誤以為在跟真人聊天

目前仍存在的揭露：IG 帳號的「AI 生成的個人檔案」標籤顯示在每個私訊畫面上方。這個標籤 MUST 保持開啟（任務 8.3 確認）。開場文字做成設定值，日後要恢復揭露只需改設定。

*替代方案*：保留「AI」的一行版本「嗨，我是晴晴，AI 戀愛顧問🌿」。使用者未採用。

## Risks / Trade-offs

- [凌晨 04:00 推播會吵醒使用者] → 使用者手機的勿擾模式會擋下通知；送出時刻做成設定，日後可改。這是使用者明確選擇的時刻
- [服務在 04:00 停機] → 啟動時補跑；超過 24 小時視窗的就送不到，記錄原因
- [打開連結時要等模型產生] → 逐段顯示，第一段約 5～10 秒；頁面先顯示對話清單與「整理中」，不是空白等待
- [多人同時打開造成 Gemini 每分鐘 15 次額度不足] → 產生失敗時頁面提供重試，不會留下半份報告；根本解法是付費方案（見 PROGRESS.md 第 5 節）
- [OpenCC `s2tw` 有一對多的字（如「发」對應「發／髮」）可能轉錯] → 只作為提示之外的保險，主要靠提示讓模型直接寫繁體；遇到誤轉再加例外詞
- [開場不再說明是 AI，違反 Meta 平台揭露政策] → 使用者已知情並決定採用（決策 10）；保留 IG 的「AI 生成的個人檔案」標籤，開場文字做成設定值，需要時可立即恢復
- [一則訊息涵蓋多段對話，最舊那段可能已超過 24 小時] → 視窗只看最後一則使用者訊息，送得出去就整則送；頁面照樣顯示所有段落

## Migration Plan

1. 備份資料庫，套用遷移（新增 `coach_digests` 表、`sessions.coach_digest_id`）
2. 部署後，對話結束不再發按鈕邀請；先前已發過邀請的對話不會被重複送
3. 第一次 04:00（或啟動補跑）會把部署後結束、尚未送過的對話送出
4. 回退：還原上一版程式即可恢復按鈕邀請；新增的表與欄位不影響舊版運作，可留著
