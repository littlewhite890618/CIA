# data-store Specification

## Purpose

定義系統正式資料庫的規範：以 PostgreSQL 儲存所有業務資料、資料表結構以可追溯的版本化遷移管理，並確保 POC 期間累積的資料能完整、可校驗地搬入正式資料庫。

## Requirements

### Requirement: 正式環境使用 PostgreSQL

系統 SHALL 以 PostgreSQL 16 作為正式環境的資料庫。遷移後的所有既有行為（webhook 接收與去重、身分歸戶、session 生命週期、話題記憶、即時訊號、教練報告、發訊紀錄）MUST 與使用 SQLite 時完全一致。

#### Scenario: 以 Postgres 連線字串啟動

- **WHEN** 資料庫連線設定指向一個可連線的 PostgreSQL 16 資料庫並啟動服務
- **THEN** 服務正常啟動，健康檢查回報資料庫類型為 postgres 且連線正常

#### Scenario: 資料庫無法連線

- **WHEN** 資料庫連線設定指向一個無法連線的 PostgreSQL
- **THEN** 服務啟動失敗並記錄明確指出資料庫無法連線的錯誤，不以缺少資料庫的狀態繼續接收 webhook

#### Scenario: 重複的 webhook 事件在 Postgres 上仍被擋下

- **WHEN** Meta 重送一則平台訊息編號已存在的事件
- **THEN** 系統不重複落庫、不重複回覆，行為與 SQLite 時相同

#### Scenario: 時間欄位保留時區

- **WHEN** 系統寫入並讀回任何時間欄位（如最後訊息時間、24 小時視窗到期時間）
- **THEN** 讀回的值帶有 UTC 時區資訊，靜默判定與視窗判斷的結果正確

### Requirement: 資料表結構由版本化遷移管理

資料表結構的建立與每一次變更 SHALL 以版本化的遷移腳本表示，並可從空資料庫一路套用到最新版本。服務 MUST NOT 在執行期間自行比對並補建欄位。

#### Scenario: 從空資料庫建立完整結構

- **WHEN** 對一個空的 PostgreSQL 資料庫套用所有遷移
- **THEN** 產生的資料表、欄位、唯一限制、外鍵與索引與目前資料模型定義一致

#### Scenario: 已是最新版本時重複套用

- **WHEN** 對已套用到最新版本的資料庫再次執行遷移
- **THEN** 不做任何變更且不報錯

#### Scenario: 資料庫版本落後時啟動

- **WHEN** 資料庫尚未套用最新的遷移就啟動服務
- **THEN** 遷移在服務開始接收 webhook 之前完成套用；套用失敗則服務不啟動

### Requirement: POC 資料一次性完整搬移

系統 SHALL 提供一次性轉檔工具，將 SQLite POC 資料庫的全部資料搬入 PostgreSQL，保留每筆資料的原始識別碼與彼此之間的關聯。

#### Scenario: 完整搬移並校驗

- **WHEN** 對已套用最新結構的空 PostgreSQL 執行轉檔
- **THEN** 每張資料表搬移後的筆數與來源相同，轉檔工具逐表輸出來源與目的筆數的比對結果

#### Scenario: 關聯與識別碼保留

- **WHEN** 轉檔完成後查詢任一則訊息所屬的對話、任一筆訊號所引用的訊息、任一份教練報告所屬的對話
- **THEN** 關聯與轉檔前完全相同

#### Scenario: 轉檔後新增資料不衝突

- **WHEN** 轉檔完成後服務開始寫入新的使用者、對話與訊息
- **THEN** 新資料取得的識別碼不與搬入的既有資料衝突

#### Scenario: 無時區的舊時間值

- **WHEN** 來源資料的時間值未標示時區
- **THEN** 轉檔時一律視為 UTC 寫入

#### Scenario: 目的資料庫已有資料

- **WHEN** 對已含業務資料的 PostgreSQL 執行轉檔
- **THEN** 轉檔工具拒絕執行並說明原因，不覆蓋、不合併既有資料

#### Scenario: 搬移中途失敗

- **WHEN** 轉檔過程中任一筆資料寫入失敗
- **THEN** 整次轉檔回復，目的資料庫維持轉檔前的狀態，並指出失敗的資料表與原因

#### Scenario: 來源資料庫不被修改

- **WHEN** 轉檔執行完成（無論成功或失敗）
- **THEN** 來源 SQLite 檔案的內容未被修改
